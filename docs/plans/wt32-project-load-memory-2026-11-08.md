# WT32 N16R2: NO MEMORY при загрузке проекта

## Причина

Загрузка в `storage::loadExt` сначала выделяет **488 908 байт одним непрерывным блоком PSRAM**, читает и проверяет проект и лишь затем заменяет текущий. Если это выделение не удалось, live-проект не изменяется. Декодер проекта сам память не выделяет.

FILE держал открытый список из 512 записей во время staging: `512 * (96 + 4) = 51 200 байт`. Список освобождался лишь после успешной загрузки. UI-волна увеличила App примерно с 82 120 до 88 224 байт до добавления новой диагностической строки; на N16R2 это пересекло существующий тесный предел.

Подтверждённый аппаратный replay на USB N16R8 ограничивал **фактически оставшуюся** PSRAM до 2 094 636 байт (на 2516 байт меньше 2 МиБ). Это проверка allocator budget, не проверка скорости quad PSRAM или полного запуска WT32 с LCD/SD/I2S. Использованы реальный конструктор App и размеры объектов текущей полной сборки; Synth и Seq принудительно размещены в PSRAM, как показывала диагностика пользователя.

| Состояние | Свободно PSRAM, байт | Крупнейший блок | Staging проекта |
|---|---:|---:|---|
| Старт, до списка | 503 896 | 499 700 | Успешно |
| Список открыт | 451 668 | 450 548 | NO MEMORY |
| Список освобождён | 503 896 | 499 700 | Успешно |

Перезапуск воспроизводит тот же набор постоянных буферов и поэтому сам по себе не устраняет причину.

## Исправление и ограничения

Выбранное имя и курсор копируются до освобождения списка. Перед storage load список освобождается; при ошибке список и выбор восстанавливаются. Transactional staging и проверка CRC сохраняются, clipboard не очищается. В Diagnostics добавлена строка PSRAM: общий свободный объём и крупнейший блок.

Дополнительно проверяется случай сохранённого undo DICE (122 700 байт). Он уменьшает свободную память и может разделять свободные области: освобождение только framebuffer даёт 692 312 свободных байт, но крупнейший блок всего 376 820 — меньше staging. Для этого случая добавлен fallback: пока framebuffer ещё занят, выполняется best-effort перенос DICE undo. Временный padding 96 КиБ помогает разместить новую копию дальше в свободной области; только после успешной копии освобождаются старый snapshot и padding. Затем framebuffer временно освобождается и загрузка повторяется. Исходный pixel-block не может быть занят snapshot во время переноса: даже при последующем отказе staging экран восстанавливается. Порядок «сначала освободить sprite, затем перенести DICE» был отвергнут ревью: при неблагоприятной фрагментации он мог мешать восстановлению экрана. В выбранном безопасном варианте повторное выделение staging на стенде проходит. На стенде копия проверена побайтно, framebuffer восстановился; следующий цикл загрузки также прошёл с loan framebuffer. Если перенос не может выделить память, исходный undo остаётся цел. Повторный отказ загрузки сохраняет live-проект и возвращает список. Во время loan redraw прогресса не может заново занять framebuffer. При неудаче восстановления экрана объект остаётся сохранённым, повтор создания выполняется позже.

## Проверки

- Регрессионные host-тесты реальных FILE/menu/list/keyboard/ParamList: сначала RED на удержании 51 200 байт, затем GREEN.
- Реальный storage с ограниченным allocator: отказ staging сохраняет live-проект побайтно, не меняет engine, ресурсы и last.txt; после освобождения памяти загрузка успешна.
- ASan/UBSan включены в host-проверках.
- Uncle Bob crapper/dryer/mutator для C++: неприменимы; установленные инструменты отвечают `No source files to analyze/mutate`, это не считается прохождением метрик.
- Финальная персональная WT32-сборка: PASS, track1=P12/bit10; исходный pins.h возвращён к bit0. Host: 15/15 unittest methods (18 FILE-сценариев), ASan/UBSan; clangd 0 ошибок; diffcheck PASS.
- OTA выполнена на 192.168.3.221: HTTP 200, тело `OK`; обычный app-image 2 192 736 байт, SHA256 `40d8912b2ee08b7796b0e3f0f6a1ad83bbdcafb8731e7512788abe44c569027b`. Проверка загрузки проекта после перезагрузки и повторного открытия Wi-Fi на самой WT32 ожидается; N16R8 allocator replay не заменяет её.
