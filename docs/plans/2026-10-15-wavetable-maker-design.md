# Свои волновые таблицы (из сэмпла и рисованием) — дизайн

Статус: принят 2026-10-15 — все рекомендации по открытым вопросам (см. «Решения»). План:
`2026-10-15-wavetable-maker.md`.

Фича «wavetable maker» для SYNTH WT. Опирается на уже существующее:
- формат и импорт таблиц: `wt_mip.h` (64 кадра × 256 точек, мипмапы, `kWtPeak`), `wt_file.h`
  (`wtDetect` / `wtImport`: раскладка 256 × N, DC убирается DFT, нормализация по пику всей таблицы);
- банк во flash синт-платы: ключ `wtKey(crc канонического источника)`, `BankJob::startImport(path, wt=true)`
  (синт паркуется), `BankImportReq kind 1`; список проекта `ProjWavetable{name, crc}` (до 32),
  `projWtSet` / `projWtPrune`; Save/Load — `AssetsSave` / `BankSync` в `/projects/<имя>/wt/<таблица>.wav`;
- ESP-обёртка `ui::wtImportFile(app, path, base, out)` (STOP PLAYBACK FIRST, уникальное имя `-2`, `-3`…,
  TABLE LIST FULL, `markDirty`) и `WtPicker` (список таблиц + IMPORT…, превью кадра 0 через `WtFrame`);
- анализ сэмплов на Teensy: `src/teensy/sample_tools.cpp` (`WavePeaks`, `Onsets`) читает
  `/mt-store/<crc>.wav` порциями в фоне стрим-планировщика, Progress раз в 200 мс. PCM сэмплов на ESP
  нет: ESP видит карту синт-платы только через `Fs*` по UART (3 Мбод, ≈ 250 КБ/с полезных).

## Цель

Две новые возможности, обе на выходе дают обычную таблицу проекта (`ProjWavetable`), неотличимую от
импортированной:

- **(a) Из сэмпла.** Область Start..End сэмпла SAMPLE-инструмента → таблица 64 × 256. Два режима:
  **CYCLE** — по 64 точкам области ищется период (питч), из каждой берётся ровно один цикл от восходящего
  нуля; **WINDOW** — область делится на 64 равных окна, каждое пересэмплируется в 256 точек.
  Нормализация (по кадру / по таблице), DC, сглаживание шва.
- **(b) Рисование.** Редактор на тач-экране: ключевые кадры (single-cycle по 256 точек) на линейке
  0..63, промежуточные кадры — линейная интерполяция. Пресеты формы (SIN / TRI / SAW / SQR) и SMOOTH.
  Аддитивный (по гармоникам) редактор — **не в этой фиче** (YAGNI), см. «Вне объёма».

## Главное решение: где считать и как едут данные

Общий конвейер для обоих режимов: **результат — WAV 16384 точек (64 × 256, моно, 16 бит) на карте
синт-платы, дальше существующий `wtImportFile(path)`** → `BankImport kind 1` → банк flash + `projWtSet`.
Никакого нового пути в банк, нового формата проекта или нового кода Save/Load.

- **(a) считает Teensy.** PCM лежит на её карте; локальное чтение SD — мегабайты в секунду против
  ≈ 250 КБ/с по линку (окно 10 с сэмпла = 880 КБ ≈ 3,5 с только на пересылку; WINDOW читает всю область).
  Так уже сделаны `Onsets` и `WavePeaks`. Новый запрос **`Msg::WtRender`** (append, `kProtocol` +1) — задача
  `Task::WtRender` в `sample_tools.cpp`: читает область порциями, строит 64 × 256, пишет WAV
  (`<путь>.tmp` → rename), отвечает. Во flash Teensy в этой задаче не пишет — это делает следующий за ним
  обычный `BankImport`.
- **(b) считает ESP.** Рисование — живой UI, интерполяция дешёвая, ключи в PSRAM ESP. Готовые 32 КБ ESP
  пишет на карту синт-платы обычным `fs::File` (FsWrite, ≈ 0,15 с), затем тот же `wtImportFile`.
  Нового сообщения не нужно.
- Вся математика — в `lib/core` (`wt_make.h/.cpp`), одинаково на обеих платах и в native-тестах; Teensy
  и ESP только кормят её данными.

Отвергнуто: (1) считать (a) на ESP через `FsRead` — медленно на длинных областях, зато без протокола;
(2) новый «залить 32 КБ таблицы прямо в банк» по линку — дублирует `BankJob`, теряется копия в библиотеке.

## Файлы и имена

- Куда пишется результат: **`/wavetables/<имя>.wav`** (корень библиотеки). Корень — потому что пресет
  SYNTH при отсутствии таблицы ищет её только в `/wavetables/<имя>.wav`: сделанная таблица переживает
  перенос пресета в другой проект. Таблица видна в IMPORT… любого проекта.
- Формат: WAV PCM 16 бит моно, 16384 сэмплов, rate 44100 (не важен), `mtcr` по данным (через
  `wavHeader`), плюс чанк `clm ` с размером кадра 256 — чтобы и сторонние синты читали его как 64 кадра.
  `wtDetect` его и так распознаёт по длине.
- **Имя:** клавиатура (как Import WAV), до 16 символов A–Z a–z 0–9 \_ -; по умолчанию: (a) имя сэмпла
  (обрезка до 16), (b) имя исходной таблицы без `*` или `DRAW`. Файл с таким именем уже есть —
  **Overwrite?** (как у сэмплов). Затем `wtImportFile` даёт имя в проекте (`-2`, `-3`… если в проекте
  другое содержимое под этим именем) — это имя и ставится в осциллятор.
- Лимиты: 32 таблицы в проекте (TABLE LIST FULL — проверка **до** расчёта), 96 КБ flash на таблицу
  (вытеснение кэша как у импорта, BANK FULL), ключей рисования до 16.

## UI

### (a) SAMPLE → To wavetable…

Пункт **To wavetable…** в меню SAMPLE (страница SMPL, рядом с Chop / Add slice; `inst_screen.cpp`
`kChop/kAdd…`). Серый без сэмпла / с MISSING. Открывает диалог в стиле `transpose_dialog`:

| Строка | Значения | По умолчанию | Смысл |
|---|---|---|---|
| Mode | CYCLE, WINDOW | CYCLE | Один цикл по питчу / равные окна |
| Norm | FRAME, TABLE | FRAME | FRAME выравнивает громкость кадров (затухающий сэмпл не «гаснет» к кадру 63); TABLE — только общий пик |
| Seam | ON, OFF | ON | Сглаживание стыка конца и начала кадра |
| Name | клавиатура | имя сэмпла | |

Сверху — длина области (мс) и `Start..End`. Кнопки **MAKE** / **CANCEL**. MAKE: проверки (стоп,
карта, место в списке) → `WtRender` с полосой прогресса «WT n/64» → Overwrite? при нужде (проверяется
до запроса) → `wtImportFile` → toast `WT имя` (CYCLE: `WT имя 58/64` — сколько кадров с найденным
питчем). Таблица попадает в список проекта; поставить её в SYNTH — обычным пикером, где сразу видно
кадр 0 и слышно C-4. Регион — `sampleRegion(inst, -1, frames, 0)` (Start..End; Reverse и петля не
влияют).

### (b) Пикер → DRAW…

В `WtPicker` перед IMPORT… строка **DRAW…**: редактор поверх рабочей области, исходник — таблица под
курсором (или в осцилляторе): её кадры 0 и 63 через `WtFrame` (8 бит — для рисования достаточно)
становятся двумя ключами. Встроенные таблицы тоже можно взять как основу; результат всегда новая таблица.

Раскладка: сверху холст 256 точек (≈ 384 × 160 px), тонко — соседние ключи (слева / справа) как
«призраки»; под ним линейка 0..63 с метками ключей и бегунком кадра (тап — выбрать ключ, перетаскивание
метки — сдвинуть его между соседями, долгий тап — новый ключ = интерполяция в этой точке; превью
промежуточного кадра при тапе мимо меток). Полоса кнопок: **SIN TRI SAW SQR** (заменить выбранный ключ),
**SMTH** (одно применение 3-точечного сглаживания, циклически), **DEL** (удалить ключ; 0 и 63 не
удаляются), **OK**, **CANCEL**.

- Рисование: перетаскивание по холсту ставит точки, между соседними событиями тача — линия (без дыр при
  быстром движении).
- Прослушивания в редакторе нет: синт играет таблицы только из flash, а запись туда требует стопа
  (вопрос 4). Звук — после OK, в пикере.
- **Без тача** (правило мануала): поворот — выбор ключа; <kbd>A</kbd> держать + поворот — сдвиг ключа;
  <kbd>Shift</kbd>+поворот — курсор по точкам холста; клик + поворот — значение в курсоре кистью
  ширины 8 точек; кнопки — как обычно фокусом. Неудобно, но полно.
- OK: при игре — «STOP PLAYBACK FIRST», редактор остаётся открыт (рисовать можно и во время игры).
  Иначе клавиатура имени → построение на ESP → запись `/wavetables/<имя>.wav` → `wtImportFile` →
  таблица ставится в осциллятор, пикер закрывается. CANCEL / долгое нажатие — выйти без изменений
  (с подтверждением, если ключи меняли).

## Алгоритмы (`lib/core/src/wt_make.*`)

Всё в int16 на входе/выходе, внутри float; итог — `int16_t src[64 * 256]`, дальше штатный `wtImport`
(DFT, мипмапы, нормализация к `kWtPeak`).

**Пересэмплирование кадра** `wtResample(x, start, len, out256)`: дробные start / len; при len > 256 —
усреднение по площади (каждая из 256 ячеек — среднее отрезка, работает как ФНЧ, без алиасинга); при
len ≤ 256 — кубическая (Catmull-Rom) интерполяция. Отсчёты берутся по модулю периода (кадр цикличен).

**WINDOW.** Область L делится на 64 окна длиной W = L / 64 (подряд, без перекрытия); кадр k =
`wtResample(окно k)`. Мин. L = 64 × 32 сэмпла (≈ 46 мс) — иначе `REGION TOO SHORT`. Seam ON: последние
F = W / 8 сэмплов окна плавно (линейный кроссфейд) смешиваются с F сэмплами *перед* началом окна (как
кроссфейд петли), так что конец переходит в начало; для окна 0 предыстория — нули с краю области не
берутся, берётся зеркало начала. Чтение — вся область одним проходом.

**CYCLE.**
1. 64 позиции анализа `p_k = from + k·(L − Wa)/63`, окно Wa = 2,5 × макс. периода (при 44,1 кГц и
   нижней границе 40 Гц ≈ 2760 сэмплов). Диапазон питча 40 Гц … 2 кГц, в лагах — по `rate` сэмпла
   (store хранит родную частоту ≤ 44,1 кГц).
2. Период: YIN-лайт — кумулятивно нормированная разностная функция d′(τ), первый минимум ниже порога
   0,15, параболическое уточнение → дробный P_k и уверенность 1 − d′. Нет минимума ниже 0,35 — кадр
   «без питча».
3. Сглаживание: медиана по 5 соседям среди найденных; «без питча» берут интерполяцию соседей. Найдено
   < 8 из 64 — ошибка `NO PITCH` (подсказка: WINDOW).
4. Начало цикла: на окне с вычтенным средним — восходящий переход через ноль, ближайший к центру окна
   (в пределах ±P/2), дробно по линейной интерполяции; из нескольких — с наибольшей крутизной.
5. Кадр = `wtResample(x, z_k, P_k)` — ровно один период → почти бесшовно. Seam ON: убрать остаточный
   скачок наклоном: Δ = экстраполяция x(P) − x(0), вычесть Δ·i/256 (снимает рост/спад амплитуды внутри
   цикла).

**Нормализация.** FRAME: каждый кадр к одному RMS (с потолком усиления ×16; кадр тише −60 dBFS
копирует соседа, чтобы не поднимать шум); TABLE — ничего (пик всей таблицы делает `wtBuild`). DC кадра
убирает `wtAnalyze` (DC не входит в гармоники) — отдельной стадии нет, но перед поиском нуля среднее
вычитается.

**Рисование.** `wtFromKeys(keys, n, src)`: ключи {кадр 0..63, 256 float}, отсортированы, ключи 0 и 63
есть всегда; кадр f между ключами a < f < b — `(1−t)·A + t·B`, t = (f − a)/(b − a). Линейная
интерполяция во времени: у ключей в противофазе середина проваливается — это видно на превью
промежуточного кадра; спектральная интерполяция — вопрос 5. Пресеты SIN / TRI / SAW / SQR — наивные
формы (band-limit делает мипмап). SMTH — `[1 2 1]/4` по кругу.

**Потоковая структура (для Teensy и тестов).** `class WtMaker`: `begin(params, from, to, rate)`;
`bool nextRead(uint32_t& at, uint32_t& n)` — какой кусок сэмпла нужен; `feed(const int16_t*)`;
`step()` — порция вычислений (YIN одного кадра режется на куски по лагам, ≤ 0,5 мс на Cortex-M7);
`done()` / `result()` / `pitched()`. Teensy-задача и native-тест гоняют один и тот же объект, читая
из файла store или из массива.

**WAV.** `wtWavWrite(src, sink)` — заголовок `wavHeader` + `clm ` + данные; тест — через `wavParse`
и `wtDetect` обратно в 256 × 64.

## Поток данных

(a): ESP `SAMPLE → To wavetable…` → проверки → `WtRenderReq{index, crc, from, to, mode, norm, seam,
path}` → Teensy `Task::WtRender` (store-файл по crc; чужой crc → `OpenFail`; путь только под
`/wavetables`) → Progress (op = WtRender, done/total = кадры) → `WtRenderRep{result, pitched}` → ESP
`wtImportFile(path, name)` (BankImport kind 1, Teensy паркует синт на время записи во flash) →
`projWtSet` → `markDirty`. Повтор запроса с тем же seq — ответ из кэша, как у `Onsets`.

(b): ESP редактор → OK → `wtFromKeys` → `wtWavWrite` в `fs::File` (`/wavetables/<имя>.wav.tmp` →
rename) → `wtImportFile` → `setTable` в осциллятор.

Протокол: `Msg::WtRender` в конец enum, `kProtocol` +1 (сейчас 7; параллельные фичи тоже могут
поднять — согласовать номер при слиянии), `scripts/link_desk.py` `PROTOCOL`. ESP-клиент —
`bank_client.cpp` (`wtRender(...)`, с прогрессом как `importWtToCache`).

## Проект: Save / Load

Ничего нового. Сделанная таблица — запись `ProjWavetable{name, crc}` + кэш банка, как импортированная:
- Save пишет её в `/projects/<имя>/wt/<таблица>.wav` (только если её использует инструмент; иначе
  `projWtPrune` убирает её из проекта — неудачные попытки сами исчезают при Save);
- Load подтягивает из папки проекта; копия в `/wavetables/` нужна лишь для пресетов и других проектов;
- ключи рисования **не сохраняются**: повторная правка открывает таблицу как кадры 0 и 63 (вопрос 3);
- Save As, перенос проекта, пресеты — без изменений.

## RAM, CPU, SD

- **Teensy:** `src` 32 КБ + окно анализа ≈ 6 КБ int16 + d′ ≈ 4,5 КБ float + буфер чтения 2 КБ — `malloc`
  на время задачи (RAM2 heap), не статикой: RAM2 уже делят `StoreJob`, `VoiceLines`, стрим. Нет памяти →
  `NO MEMORY`. CPU: YIN ≈ 2760 × 1100 ≈ 3 M операций на кадр × 64 ≈ 0,2–0,4 с на M7, порциями в фоне.
  CYCLE читает 64 окна ≈ 350 КБ, WINDOW — всю область (10-минутный сэмпл ≈ 53 МБ ≈ 5–10 с, с прогрессом
  и отменой CANCEL).
- **ESP:** ключи 16 × 1 КБ float + 32 КБ результата + полоса превью — PSRAM, только пока открыт редактор.
- **SD и стриминг:** и `WtRender`, и импорт во flash требуют **остановленного воспроизведения**
  (как сейчас импорт таблиц) — запись 32 КБ и чтение области не конкурируют со стримом; известная
  проблема «запись на карту стопорит чтение на 150–430 мс» не задевается. Рисовать можно во время игры.

## Тесты (native)

Новый `test/test_wt_make`:
- `wtResample`: константа → константа; синус ровно 256 точек → тождество; синус 1024 точки периода →
  256 точек с ошибкой < 1 LSB·4; площадь не даёт алиасинга (синус выше Найквиста цели → ≈ 0).
- YIN: синус / пила / квадрат 55, 110, 440, 1760 Гц при 44,1 и 22,05 кГц — период ±0,1 сэмпла; шум →
  «без питча»; глиссандо 220 → 440 Гц → монотонные P_k; < 8 питчей → `NO PITCH`.
- Нуль: кадр CYCLE синуса начинается с восходящего нуля (|x0| < 1 % пика, x1 > x0); корреляция с
  идеальным синусом > 0,999.
- Шов: после Seam ON |f[255] + (f[255] − f[254]) − f[0]| < 2 % пика для затухающего синуса и для
  WINDOW шума.
- DC-смещение входа +8000 → итоговая таблица (через `wtImport`) со средним ≈ 0.
- Norm FRAME: экспоненциально затухающий синус → RMS кадров 0 и 63 различаются < 1 дБ; тишина в конце
  → копия соседа, не шум.
- `wtFromKeys`: кадр-ключ = ключ; середина = среднее; два ключа → все 64 кадра; сортировка ключей.
- `WtMaker` на массиве и на «рваных» чтениях (куски по 1000) даёт тот же результат.
- `wtWavWrite` → `wavParse` + `wtDetect` = 256 × 64 → `wtImport` Ok.
- `test_link_msg`: `WtRenderReq/Rep` round trip, новый `kProtocol`.
- `test_bank_ops`: импорт сделанного WAV даёт тот же `wtKey`, что `wtImport` массива `src`.

Без нативных тестов (руками на железе): `Task::WtRender` на Teensy, диалог, редактор, Overwrite.

## Риски

- **SD-запись и стрим** — снят требованием стопа; если позже разрешить render во время игры, длинный
  WINDOW-проход отнимет полосу у 16 стрим-голосов.
- **RAM2 Teensy** — 40+ КБ на время задачи; при фрагментации `malloc` может не дать → понятная ошибка,
  не падение.
- **Качество CYCLE** на полифонии / шуме / сильном вибрато — честное «58/64» в toast и подсказка WINDOW.
- **Линейная интерполяция ключей** — провалы громкости между противофазными ключами (Norm не лечит,
  `kWtPeak` по всей таблице).
- **Протокол** — несколько параллельных фич двигают `kProtocol`; конфликт номеров при слиянии.
- **Засорение `/wavetables`** — каждая сделанная таблица = файл в корне; удаляются только с компьютера.

## Вне объёма (YAGNI)

Аддитивный редактор гармоник; спектральный морфинг ключей; выбор числа кадров ≠ 64; таблица из слайса
(только Start..End); перезапись существующей таблицы проекта на месте (всегда новая); удаление таблиц из библиотеки
с устройства; звук в редакторе рисования до OK.

## Открытые вопросы

1. Где считать (a): **Teensy, новый `WtRender` [default]** / ESP через `FsRead` (без протокола, медленно
   на длинных областях).
2. Куда класть результат: **`/wavetables/<имя>.wav` [default]** (пресеты находят) / `/wavetables/made/`
   (чисто, но пресеты не найдут без правки поиска) / только временный файл (таблица живёт лишь в
   проекте).
3. Ключи рисования: **не хранить, правка с кадров 0 и 63 [default]** / чанк `mtkf` с номерами ключей в
   WAV библиотеки (надо, чтобы Save/экспорт его сохранял).
4. Звук в редакторе рисования: **нет, после OK [default]** / временная таблица во flash на каждое
   прослушивание (запись во flash = стоп).
5. Интерполяция ключей: **линейная [default]** / спектральная (модули гармоник, без провалов; +FFT на ESP).
6. Источник (a): **Start..End [default]** / выбранный слайс, если выбран маркер слайса.

## Решения (2026-10-15)

Приняты все рекомендации: (1) (a) считает Teensy, `Msg::WtRender`; (2) результат в `/wavetables/<имя>.wav`;
(3) ключи рисования не хранятся; (4) звука в редакторе нет, слушать после OK в пикере; (5) ключи
интерполируются линейно; (6) источник — Start..End.

Уточнения, принятые при реализации:
- **Протокол 10** (после Scala = 8 и сцен = 9; GEN протокол не двигал). `WtRenderRep{result, err, pitched}`:
  `result` — `BankResult` (доступ к сэмплу, чтение, память), `err` — `WtMakeErr` расчёта (`REGION TOO SHORT`,
  `NO PITCH`, `SILENT`); `BankResult` не расширяется.
- **CYCLE в два прохода по карте:** проход 1 читает 64 окна анализа и находит периоды, сглаживание медианой,
  проход 2 читает окна заново и вырезает циклы (хранить 64 окна — 350 КБ). Восходящий ноль ищется в
  `[Wa/2 − P, Wa/2)` (чтобы `z + P` не вышел за окно), из нескольких — самый крутой.
- **WINDOW потоково:** при L ≥ 16384 каждая из 16384 ячеек — среднее по площади своего отрезка (сэмпл как
  ступенька), при L < 16384 — Catmull-Rom; в памяти только текущий кадр. Seam считается в пересэмплированной
  области: последние 32 точки кадра (W/8) смешиваются с последними 32 «сырыми» точками предыдущего кадра,
  которые и предшествуют началу окна; для кадра 0 — зеркало его начала.
- **Хранение кадров:** каждый кадр сразу пишется в int16 с полной разрядностью (свой масштаб к пику 32767),
  нормализация (FRAME: к максимальному RMS, усиление ≤ ×16, кадр тише −60 dBFS копирует соседа; TABLE —
  только общий масштаб) и общий масштаб к пику 30000 — в конце. Память Teensy: результат 32 КБ + окно
  анализа (float) ≈ 11 КБ + d′ ≈ 4,5 КБ + буфер чтения 2 КБ, `malloc` на время задачи.
- **Отмены у WtRender нет** (как у `Onsets`): длинный WINDOW-проход по 10-минутному сэмплу идёт с прогрессом
  до конца; область задаётся маркерами, так что длинный проход — осознанный выбор.
- **Редактор рисования** без тача управляется так, как описано выше; долгий тап на линейке заменён на
  кнопку **KEY** (новый ключ в позиции бегунка = интерполяция) — тот же результат без таймера
  долгого нажатия, который у тача на этом экране занят выходом. Ключ двигается перетаскиванием метки.
- **Тесты, отличия от списка выше:** шов WINDOW проверяется на синусе с нецелым числом периодов в окне
  (у белого шума соседние ячейки независимы, «< 2 % пика» для него недостижимо); период YIN ±0,1 сэмпла —
  для синуса, пила / квадрат ±0,3 (у них d′ у периода V-образная), и пила / квадрат короче 20 сэмплов на
  период не проверяются (сплошной алиасинг, YIN берёт два периода). Прогресс показывается как «WT NN%».
- Seam WINDOW — приподнятый косинус (линейный кроссфейд оставлял излом наклона ≈ 6 % пика у конца).
