# WT32: приоритет внутренней памяти для аудио

## Причина и изменение

На WT32 N16R2 объединённый блок Synth + Sequencer занимал 84 400 байт внутренней RAM. После освобождения 5 120 байт за счёт переноса офлайн-анализа сэмплов из IRAM этот блок стал помещаться, но линии реверберации оказались в quad PSRAM. Первый пользовательский повтор не показал выигрыша CPU: 45,5% → 46,5% при разных длительностях записи. Это исправило размещение Synth, но не общую стоимость аудио.

Новая политика резервирует внутреннюю RAM для Synth (49 264 байта) и линий реверберации. Sequencer (35 136 байт) один раз размещается в PSRAM и больше не переносится при включении Wi-Fi. Общий объём аудиоданных не увеличивается. Для Wi-Fi Synth и линии реверберации по-прежнему освобождают внутреннюю RAM; при закрытии Wi-Fi восстанавливаются с безопасным сохранением прежнего буфера при отказе выделения или парковки аудиозадачи. Начальный переход Synth в PSRAM при нехватке внутренней памяти также допускает последующую попытку восстановления.

FM, аудиочастота, число голосов, алгоритмы DSP и пороги цветного индикатора CPU не менялись. Исправление загрузки проекта с временным освобождением framebuffer сохранено.

## Замеры на настоящей WT32

Временная диагностическая прошивка использует штатные движок, I2S, SD, LCD и экран FILE → SYSTEM → Diagnostics. Она загружает TUTU-TUDUTU, запускает P01 в LOOP с фиксированным seed 0x5eed, прогревает 8 секунд, затем записывает три последовательных окна по 8 секунд. Проект и настройки устройства не сохраняются. После остановки автоматически открывается обычный Wi-Fi transfer; профили скачиваются по HTTP. Дополнительные записи журнала выполняются между окнами.

Контрольный повтор A2/B2 на одинаковой модели проекта:

| Политика | Среднее render | Реверберация | Жёлтые интервалы CPU | Красные / DMA stalls |
|---|---:|---:|---:|---:|
| A2: Synth + Seq INTERNAL, RVB PSRAM | 1964 мкс (49,10%) | 542 мкс | 23 / 48 | 0 / 0 |
| B2: Synth + RVB INTERNAL, Seq PSRAM | 1529 мкс (38,23%) | 167 мкс | 7 / 48 | 0 / 0 |
| C: та же память, строка Card кэшируется | 1539 мкс (38,47%) | 167 мкс | 4 / 48 | 0 / 0 |

Среднее время уменьшилось на 435 мкс (22,15%, или 10,87 процентного пункта CPU). Из них 375 мкс даёт реверберация. Пиковый блок: 4996 → 4474 мкс, то есть отдельные пики выше 4 мс ещё остаются. В первом независимом повторе A/B также получено 48,7% → 38,5% и 32/48 → 5/48 жёлтых интервалов; их число меняется с взаимной фазой UI и аудиозадач.

Оба контрольных запуска автоматически вернули Wi-Fi; оба образа приняты OTA с HTTP 200 / OK. Частота отрисовки практически одинакова: около 11 кадров/с. Файл проекта до и после B полностью совпал: SHA256 `3e667e826e0b749057a4ca4c52d12d5426d77d3fc4615b4db6ace299e8d26322`.

Первоначальный FNV сериализованной модели оказался непригоден для строгого сравнения: `autoload` копирует также неинициализированный хвост имени после NUL, а `saveProject` включает его и производную CRC в поток. Host-воспроизведение на этом же MTP подтвердило разницу только в четырёх незначащих байтах имени и CRC. Для контрольного повтора диагностический hash нормализует хвост имени и исключает четыре байта производной CRC (`hash_excludes_crc=1`), не меняя живой Project. На host ожидаемая сумма этого проекта — `4363edfc`. В A2 и B2 она совпала; совпали также исходные суммы `06a49af7`, размер 66420 байт и seed. Средние числа FM/SYNTH/sample-голосов совпали в пределах точности записанных счётчиков; изменение ctlMod менее 0,021%.

На экране Diagnostics видна строка Card: её текущий formatter вызывает `SD.totalBytes()` и `SD.usedBytes()` при каждой отрисовке. В A/B это поведение оставлено одинаковым. В отдельном опыте C предварительный снимок Card устранил повторные чтения и форматирование, но среднее время стало примерно на 10 мкс больше, а пик изменился всего с 4474 до 4404 мкс. Заметного выигрыша не подтверждено; кэш Card в production не перенесён. Семантическая сумма C также `4363edfc`, файл проекта не изменён, Wi-Fi вернулся автоматически. Это короткий опыт всей строки, а не изолированный замер SPI; различие числа жёлтых интервалов само по себе не доказывает пользу кэша.

## Проверки и ограничения

- 16 host-тестов прошли; среди них 10 сценариев владения и перемещения памяти, отказы выделения/парковки и 100 циклов переноса.
- GCC-сборка обычной WT32-прошивки прошла; в ELF отсутствуют автотестовые hooks. Персональная кнопка Track 1 сохранена на P12 / bit 10; исходная таблица пинов восстановлена после сборки.
- clangd: 0 ошибок для новой политики памяти и host-проверки.
- На N16R8 с ограниченным бюджетом памяти прошли 30 циклов STA → scan → OFF, включая фрагментацию с крупнейшим свободным блоком 51 188 байт. Это дополнительные проверки владения памятью, а не замена WT32 и не проверка ассоциации с AP/HTTP на стенде.
- UncleBob crapper/dryer/mutator не поддерживают C++; результат `No source files` отмечен как N/A, а не успешный gate.

Сырые журналы: [bench/wt32-priority-2026-11-08](bench/wt32-priority-2026-11-08/).

Статус: контрольные замеры закончены. Обычный образ без автопрофайлера установлен по OTA на `192.168.3.221`: HTTP 200, ответ `OK`, 2 193 056 байт, SHA256 `6f84c1e86528df37a6664a5ce669af8759ee65d856a252ff7b073720e8a16e8b`. В финал вошла только новая политика памяти; эксперимент Card не переносился. Нормальная прошивка после перезагрузки не открывает Wi-Fi автоматически. Без USB независимая телеметрия обычной загрузки недоступна; работоспособность штатного Wi-Fi пути проверена всеми диагностическими запусками на этом же устройстве.
